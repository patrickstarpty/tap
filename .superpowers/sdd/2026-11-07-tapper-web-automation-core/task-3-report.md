# Task 3 implementation report

## Scope and production handoff

The frozen `kind: "browser"` native workflow branch enters `CodingRuntime` before the native graph/model path. The runtime starts one OpenCode 1.19.5 `serve --pure` session in a network-none, nonroot, read-only-root coding container; it grants only task-local `/workspace` writes and the fixed `browserctl` inspector helper. `browserctl` reaches the real Task 2 project-scoped HTTP API through a private mailbox, so the model receives actual page observations before writing `/workspace/flow.spec.ts`. The script is hash-checked, submitted as a Task 2 bundle, executed in a fresh Task 2 browser execution container, and optionally repaired once in the same OpenCode session. Frozen replay directly calls Task 2 replay and records `replay_model_calls=0` without a model/container.

Task 4 should freeze a request containing `kind="browser"`, natural-language `goal`, `model_alias="qwen-plus"`, `root` (`agent_id="orchestrator"`, nonempty registered `revision_id`, `instruction`, `description`), `candidates`, `requested_ids`, `browser.start_url`, `browser.expected_result` (nonempty bounded text), `browser.allowed_origins`, `browser.input_data`, `browser.input_sha256` (SHA-256 of canonical JSON), optional `browser.execution_limits`, optional `browser.replay_execution_id`, `budget_limit.model_calls` and **positive** `budget_limit.cost_micros`, plus a timezone-aware `deadline_at`. `browser.start_url` must belong to the frozen allowed origins; the start URL and expected result enter the same OpenCode prompt as the goal. Native's historical `TAP_WORKFLOW_MAX_COST_MICROS=0` omits the cost limit; browser tasks must instead freeze a finite positive cap. `browser.replay_execution_id` bypasses the model even when the other frozen fields remain present. The browser API is configured with loopback `TAP_BROWSER_API_ORIGIN`, project ID and access token; the coding settings are `TAP_BROWSER_CODING_*` in `.env.example`. Configure the current exact coding image ID, alias, 129024 max input tokens, 2048 output tokens, and prices from the frozen LiteLLM `/model/info` metadata. The production model request/response raw caps are 131072/1048576 bytes, with distinct mailbox JSON/base64 envelopes of 196608/1400000 bytes.

`CodingResult` has `status` (`passed`, `failed`, `blocked`, `canceled`, `unknown`), `provider_session_id`, `bundle_ref`, `execution_ref`, `usage`, `terminal_evidence`, optional `input_request`, and `replay_model_calls`. A model-detected missing value or external login/CAPTCHA writes a bounded `/workspace/tapper-input-request.json` with `reason` (`missing_input` or `external_block`) and a nonempty `question` of at most 2000 bytes; this yields `blocked` and native `await_input`. A final OpenCode explanation alone is never success: the runtime requires a digest-checked script and a passed Task 2 execution receipt. `failed` retains the real bounded failure/evidence; `canceled`/`unknown` cannot be shown as passed. Native dispatch persists `browser.coding_result` with task/node/attempt, refs, usage and replay count, then applies node/task outcome. Task 4 should project that event and fetch evidence through the project-validated Task 2 service, not host paths.

Task 4/5's isolated full Chat/product test must provision *separate* Task 2 browser and TAP AI workflow MySQL databases/migrations and register a real root agent revision in the TAP AI catalog before dispatch. A synthetic `revision_id` without that catalog row violates the workflow node FK. The direct runtime experiment below uses a real task/lease/action budget but no node; it is not a full Chat/dispatch product E2E.

## Fix round 1: review C1 and I1–I4

The reviewed five findings are resolved in the same production paths. The coding container now receives a read-only mailbox parent with only `requests` and `acks` writable; `responses` is read-only. Model-shim publishes temporary files inside the writable child mounts. Host mailbox operations use opened `O_DIRECTORY|O_NOFOLLOW` directory descriptors, verify their inode bindings, and perform reads, links, unlinks and cleanup relative to those descriptors. An adversarial replacement of `requests` or `acks` with a symlink to an owned sentinel cannot read or delete the sentinel. The first real integration found a concurrent `*.tmp` publication race after this mount change; the host now ignores only valid-identity unpublished staging names and continues rejecting malformed published requests.

For cancellation, `CodingRuntime` returns `CodingResult(status="canceled", terminal_evidence.stop_confirmed=true)` only after an authoritative Task 2 canceled receipt and, for a model run, confirmed coding-container and inspector-session stops. Replay uses its Task 2 canceled execution receipt and never enters the model. Native dispatch persists `browser.stop_confirmed` with the current `node_id`, `attempt`, and lease `execution_token`. `MysqlWorkflowStore.stop_evidence` accepts that proof for a running browser node only when it matches the locked current task, lease, node and attempt and all action reservations for the lease are settled. Non-browser nodes retain their checkpoint requirement. Unknown stops, stale attempts and foreign execution tokens do not acknowledge cancel. Task 4 may project an applied task cancel as canceled only after this store proof; `browser.coding_result` alone is not stop proof.

`DockerCodingContainer.stop()` now makes a bounded three-second exact-identity inspect after stop/remove attempts. Only exact `ID false` or an exact `No such object: ID` response confirms stop. Docker daemon, permission, transport, running or timeout outcomes remain unknown. BudgetGate shutdown occurs off the owning event loop; the runtime then awaits each scheduled durable callback before terminal return or lease release. A timed-out reservation is drained and, if it later committed, receives one compensating zero-cost settlement; any unconfirmed callback prevents success. The reporter and dispatch both measure the *complete* compact UTF-8 JSON outputs array against 32768 bytes, including array/object overhead. Invalid or oversized output becomes an explicit failed result, while valid non-ASCII business values remain accepted.
