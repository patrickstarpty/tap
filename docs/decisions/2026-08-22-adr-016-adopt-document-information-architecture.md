# ADR-016：采用文档信息架构

## 背景

TAP 的架构、提案、决策、计划、评审、契约和来源记录此前混放在 `docs/` 根目录。随着文档增加，读者难以按稳定职责发现信息，生命周期状态也容易与物理路径混淆。

## 决策

采用六个稳定职责目录：`architecture/`、`proposals/`、`decisions/`、`plans/`、`reviews/` 和 `reference/`。内容文档采用带日期的文件名；RFC、ADR 和 Plan 使用各自的生命周期元数据；每个目录维护直属子项索引；根 `AGENTS.md` 路由到文档治理规范和 RFC/ADR 模板。

## 考虑过的方案

### 保持扁平目录

仅保留现有扁平目录会继续混合规范架构、提案、决策和计划，随着文档增长仍需再次迁移，因此拒绝。

### 使用生命周期目录

将文档放入 `draft/`、`accepted/` 或归档目录会在状态变化时改变路径，造成链接破坏和 Git 噪声，因此拒绝。

### 同时引入文档站或 CI

文档站和 CI 有长期价值，但会扩大本次变更范围；本次仅建立信息架构和治理契约，因此拒绝在此变更中引入。

## 后果

后续文档必须遵循目录职责、命名、元数据、索引和链接修复规则。状态通过 front matter 演进，不通过移动文件表达；新建或替代 ADR 时必须维护双向替代关系。
