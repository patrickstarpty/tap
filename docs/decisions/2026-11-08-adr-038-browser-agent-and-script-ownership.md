# ADR-038：浏览器 Agent、脚本整理与执行权威分工

## 背景

用户明确目标是像 Codex 一样实时操作浏览器完成业务，默认生成脚本供用户回放，并选择 TAP 管理的独立浏览器，支持查看过程、登录和人工接管。2026-11-08 用户确认 browser-use 负责网页任务、OpenCode 负责整理成功操作、TAP 负责会话控制与证据的分工。

## 决策

TAP AI workflow 持有父任务、阶段、用户输入和累计预算；browser-use 作为其受控模型 runtime 负责实时浏览器任务，OpenCode 在业务结果与轨迹冻结后负责脚本整理。两个 Agent 使用现有 LiteLLM 接入边界，各自调用均计入同一任务，不并行指挥同一个浏览器。

TAP 非 AI `browser_automation` 继续持有浏览器会话、控制权、动作与执行回执、不可变脚本包及证据对象。实时浏览器控制同一时刻只授予 browser-use、用户或回放执行器之一；OpenCode 只获得脱敏证据包，不获得现场浏览器控制权。跨应用通过项目作用域合同协作，不跨应用 import。

业务完成与脚本生成、回放验证分别记录。默认生成脚本不自动重做已成功业务；用户主动回放才创建新执行。正常冻结脚本回放不调用模型，需修复时建立有预算的独立阶段和新版本。生成失败或回放失败不能覆盖原始业务结果。

本决定局部调整 [ADR-037](2026-11-07-adr-037-browser-automation-core-first.md)中的 OpenCode 主导浏览器生成/执行路径和仅取消边界；保留其应用归属、隔离、预算、不可变证据及非正式测试资产约束。详细产品与验证边界见[设计](../superpowers/specs/2026-11-08-tapper-browser-agent-and-replay-design.md)。决定被接受不等于新实现已交付；旧验收记录继续只证明旧模式。

## 考虑过的方案

继续让 OpenCode 同时承担浏览器任务和脚本生成可复用现有代码，但与此次明确的职责划分不同。直接把 browser-use 历史作为最终回放资产仍依赖其运行时，不能满足独立可维护脚本的边界。让两个 Agent 共享可写浏览器会使动作归属和恢复含糊，因此采用顺序交接与单一控制权。

## 后果

新增 browser-use 适配、受控 CDP、人工接管和动作到脚本的证据映射。现有任务、预算、存储、项目边界与 Playwright 执行器可复用，但需扩展在线执行合同，不能只换提示词。详细设计需评审，固定版本与模型兼容、无重复动作控制及真实产品链路需分别验证；维持本机回环范围，不改变 V1 或正式测试资产发布规则。
