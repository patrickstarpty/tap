# Tapper 推荐问题设计

日期：2026-09-30。归属 [V1 总纲](../plans/2026-09-29-v1-roadmap.md) 能力 1“可靠问答”，实施放在子项目 3。

## 背景

新对话页目前显示三个写死的寿险快捷提问（`apps/tap-ai-frontend` 的 `copy.chat.quickPrompts`），它们来自原型示例数据，与真实项目的知识库无关，点击后常得到“资料不足”。推荐问题应根据项目知识库和用户使用情况生成，并保证点击后能得到有依据的回答。

## 目标

- 新对话页显示按用户和项目生成的推荐问题，替换写死的快捷提问。
- 显示出来的推荐问题点击发送后，至少 90% 得到有依据的回答。
- 不显示失效或过期的推荐。
- 其他用户的提问原文不进入模型输入，也不展示给当前用户。

## 非目标

- 对话进行中的追问建议。
- 用户手动收藏或编辑推荐问题。
- 推荐质量的在线学习（点击率反馈）。

## 架构与数据流

后端在 `apps/tap-ai-backend` 的 `chat` 模块新增推荐问题能力，复用现有后台任务、模型网关（`ai` 模块）和授权检索（`knowledge` 模块的 `AuthorizedRetrieval`），不新增基础设施。

```mermaid
flowchart LR
  T[触发：知识发布 / 对话完成 / 每日] --> J[刷新任务<br/>按用户+项目+语言]
  J --> I[收集输入]
  I --> G[模型网关生成候选<br/>最多 8 个]
  G --> V[以当前用户权限<br/>检索校验依据]
  V --> S[(MySQL 推荐缓存)]
  S --> R[GET 推荐接口<br/>读取时再过滤]
  R --> UI[新对话页推荐区]
```

1. **触发**：以下情况为（用户，项目，语言）排入一次刷新任务：
   - 项目发布了新知识（对该项目的所有活跃用户）。
   - 用户完成一轮对话。同一用户同一项目 10 分钟内最多刷新一次。
   - 每日一次兜底刷新。
   - 读取时有推荐被过滤（见“读取与过滤”）。
2. **收集输入**：
   - 知识库主题：已发布文档的标题和章节，以及知识图谱中的主要实体。
   - 个人使用情况：该用户在本项目最近的有依据回答轮次中的提问文本与所选来源。
   - 项目热门：其他用户常用来源和图谱实体的**统计次数**。不包含其他用户的提问原文。
   - 冷启动：没有个人历史时只用知识库主题和项目热门；知识库为空时不生成。
3. **生成**：经模型网关以结构化输出生成最多 8 个候选问题，每个附对应来源 ID，语言与目标语言一致。
4. **依据校验**：每个候选问题以当前用户的授权上下文执行一次检索，达到依据阈值才保留；这同时保证不推荐用户无权访问的资料。
5. **缓存**：通过校验的问题写入 MySQL 新表，按（用户，项目，语言）存储，记录生成时间、依据来源 ID 及每个来源在生成时的发布版本。每次刷新整体替换该用户该项目该语言的旧推荐。

## 读取与过滤

新增接口 `GET /projects/{project_id}/prompt-suggestions?locale=<en|zh>`，返回推荐问题列表，每项含 ID、问题文本和来源（ID、名称）。读取时逐条过滤，满足任一条件的推荐不返回：

- **来源失效**：任一依据来源被删除、取消发布，或当前用户已无访问权限。
- **内容过期**：任一依据来源存在比记录版本更新的发布版本。

有推荐被过滤时，排入一次刷新任务（受 10 分钟节流约束）。过滤后为空则返回空列表。接口直接读缓存，不调用模型。

## 界面

交互先在 `apps/web` 的 `/prototype` 设计，`apps/tap-ai-frontend` 按原型实现。

- 推荐区位于新对话页输入框下方，替换写死的快捷提问；对话开始后不再显示。
- 一次显示 4 个推荐。每个推荐为一张卡片：问题文本；下方小字“基于《来源名》”，多个来源时为“基于《A》等 N 份资料”。
- 点击卡片：问题填入输入框，光标置于末尾，不自动发送。当前未选知识来源时，选中该推荐的来源；已有选择时追加，不覆盖。
- “换一批”：推荐总数超过 4 个时显示，点击轮换到下一批。
- 推荐语言跟随界面语言。

| 状态 | 表现 | 原型中的触发 |
| --- | --- | --- |
| 正常 | 显示 4 个推荐卡片 | 自然 |
| 换一批 | 显示下一批 | 自然 |
| 语言切换 | 显示对应语言的推荐 | 自然 |
| 无推荐 | 推荐区不显示 | 自然：在 Library 删除全部来源 |
| 加载中 | 4 个占位骨架 | 注入 |
| 接口失败 | 推荐区不显示，不报错 | 注入 |

原型的示例推荐基于现有示例文档（如寿险核保指南、受益人变更流程），注入状态沿用 `prototypeFaults.ts`，并加入[原型状态截图集](../../guides/2026-09-29-prototype-state-gallery.md)。

## 验证

- **后端单元测试**：依据不足的候选被丢弃；无权访问的来源不进入推荐；来源删除、取消发布或有新版本时推荐不返回并排入刷新；模型输入中只含其他用户的来源与实体统计，不含其提问原文；刷新节流为 10 分钟。
- **契约**：新接口经 `make contracts` 生成 OpenAPI 与前端类型，并有契约测试。
- **集成测试**：新表读写，以及触发 → 生成 → 校验 → 读取的完整链路，模型使用确定性替身。
- **前端**：原型与 TAP AI 前端各自的组件测试，覆盖点击填入并追加来源、换一批、隐藏条件；更新状态截图集。
- **真实模型冒烟**：在 `TAP_RUN_TAPPER_REAL_MODEL_SMOKE=1` 下生成一次推荐，确认问题可读且通过依据校验。
- **业务验收**：在一个真实项目中逐个点击并发送显示的推荐问题，至少 90% 得到有依据的回答；通过能力 5 的可观测性核对。

## 实施顺序

1. 清理 TAP AI 前端中写死的原型内容，包括去掉硬编码快捷提问（推荐功能上线前该区域不显示）。
2. 在 `/prototype` 设计推荐交互。
3. 后端实现推荐生成、缓存、过滤与接口。
4. TAP AI 前端按原型实现。

`docs/architecture.md` 在第 3 步补充推荐问题的数据流。
