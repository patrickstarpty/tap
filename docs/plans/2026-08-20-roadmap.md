# TAP 交付路线图

TAP 的长期主体仍是 BrowserStack-like Test Automation Platform，但从 2026-09-02 起采用 **Intelligence 价值验证先行** 的交付顺序。当前 Phase 1 先验证 AI 能否把不完整输入转成可追溯、可审查、可评测的测试工程产物；此后再建设正式测试资产、真实执行、证据和团队治理。每一阶段用可重复评测和安全证据退出，不以日期或演示代替完成标准。

当前规范性范围见 [RFC-007：Phase 1 Intelligence Layer 探索](../proposals/2026-09-02-rfc-007-phase-1-intelligence-layer-exploration.md)，阶段决策见 [ADR-019](../decisions/2026-09-02-adr-019-phase-1-intelligence-layer-exploration.md)。旧 RAG Foundation 和 Knowledge Chat 设计仍是可复用的知识面目标，但不再是当前 Phase 1 的完成条件。

## 已交付基线：Athena 本地知识切片

Athena 已用 Python/FastAPI 和 React/Vite 交付来源优先的本地 `doc` 纵向切片：文档上传、MySQL ledger/Outbox、Redis 唤醒、Azurite Artifact、typed parse/chunk、固定模型路由、本地 Milvus 投影、来源限定回答和 claim citation。这些 revision/hash/anchor、引用、恢复和幂等模式作为 Intelligence Layer 的输入基础保留。

该增量仍只是 loopback、无认证、无 OCR 的本地 Demo；它没有通用 Context 授权、Intelligence Task/Attempt、Artifact Review、真实测试运行或企业四索引。因此不得把 Athena Answer、Chat Turn 或 Ingestion Job 泛化成新控制面，也不得把已交付 Demo 描述为 Phase 1 Intelligence 已完成。

## Phase 1：TAP Intelligence Lab（当前重点）

### P1.0：契约与评测先行

- 冻结 `AutomationBrief`、`ContextSnapshot`、`RuntimeContextPacket`、`InputManifest`、goal-bearing `RuntimeInvocationEnvelope`、共享 `RuntimeLineageV1`、append-only proposal Schema registry、符合 `openai-structured-outputs-subset-v1` 的 per-invocation root output Schema、Proposed/public Claim、四个 Artifact body、不可变 `IntelligenceArtifactEnvelope`、append-only `ArtifactValidation`、派生 `ArtifactView`/`ArtifactDetail`、`AttemptUsageV1`、`ReviewPackage` 和 `ArtifactReview` v1。
- 建立至少 24 个 Golden Tasks，按 assumption-first、source-grounded、repository-informed 和 evidence-informed 四个 lane 单独报告。
- 先交付 deterministic fake baseline，锁定 Runtime Schema subset linter、Citation、虚假执行状态、越权和 Prompt injection 门禁；opt-in 真实模型 smoke 的首例必须用 exact root Schema 验证 provider 实际接受该子集。
- 提供互不混入的 `make intelligence-eval`、`make intelligence-integration`、`make intelligence-e2e` 和显式 opt-in `make intelligence-real-smoke`。

### P1.1：Grounded Intelligence

- 创建 Brief 时只强制要求 `goal`；P1.0–P1.2 wire 只接 goal、可选人工步骤和用户选择的 `ready` Knowledge Source。零散 Requirement 可作为 goal/资料内容输入；Project、Release、仓库和失败材料的 typed relation 后置。
- 把实际拿到的输入、已知缺失、版本、hash、授权和引用范围固定为不可变 Context Snapshot。
- 交付 assumption-first 和 source-grounded 两条路径，产生版本化 Intelligence Report、Assumption Register 和 Automation Blueprint；P1.2 再由可信 Controller 汇总 Review Package。
- 用 `evidence | inference | assumption | unknown` 区分重要结论；没有资料时不伪造 Citation，没有真实执行时固定 `execution_status=not_run`。

### P1.2：Durable Agent Task

- 新建独立 `IntelligenceTask`、`TaskStep`、`Attempt`、Event、Outbox、Artifact 和 Review 持久化模型，不复用 Chat Turn 或 Knowledge Ingestion Job。
- 每个 Attempt 固定 packet、manifest、invocation 和 root-Schema refs，并将 Runtime result 与 Artifact seal public body 保存为可校验、可恢复的 canonical bytes，而不是只保存 hash。
- Runtime 使用 `prepare -> register -> reauthorize -> activation_intent -> activate`：未激活 launcher 不接收 invocation 也不发起模型请求；第二次即时授权通过后才能单次激活。
- 支持可恢复任务时间线、取消、超时、失败、新 Attempt 重试、lease/fencing 和 Reconciler 对账。
- 在 provider-neutral `AgentRuntime` 端口后以 Codex 作首个可关闭的 read-only Adapter，不向公共 API 或 UI 暴露供应商模式。
- 将 Runtime、TAP Tool Gateway、可信 Artifact Broker 和独立 Validator 分开；Artifact 本体不因验证到达而改写，任何越界、未识别事件或状态不明均 fail closed。
- 交付 Task Timeline、Artifact revision、Citation/lineage、Review decision 和 Markdown + JSON manifest 导出。

### P1.3：条件开启的实验 Lane

- Failure Intelligence 只读 immutable failure bundle，严格区分 observed、inferred 和 unknown。
- Automation Engineering Lab 只在固定 Playwright + TypeScript Repository Profile、凭据隔离、workspace escape、网络、Broker path scan、patch policy 和独立 Validator sandbox 全部通过后开启。
- 无测试仓库时只能从固定 template tree 生成 Code Bundle；有仓库时只能在固定 commit 副本生成 Candidate Patch。产品源码始终只读。
- 该 Lane 使用独立 feature gate，关闭后 P1.1/P1.2 回归必须全部通过。

### P1.4：Retain / Revise / Stop

- 在固定版本与观察窗口运行真实模型评测，按 lane 报告质量、引用、安全、诚实性、时延、成本和人工采纳。
- 对每项能力作出 `retain | revise | stop` 决定；只有被保留的 Artifact 契约和 AI 能力进入后续 BrowserStack-like 平台。

### Phase 1 出口标准

- 只提供 `goal` 也能创建、恢复、审查和导出一个 Task；缺失输入和假设明确可见。
- Source-grounded 重要结论全部绑定当前 Context Snapshot 的可解析 Citation，越权读取与跨 scope 泄露为 **0**。
- Task/Attempt 终态、取消、重试和 Artifact/hash 对账可用 deterministic fake 重放。
- 所有 Artifact 绑定 input manifest 和共享 Runtime/producer lineage，验证以 append-only 记录与精确 pin 呈现；没有 Execution Provider evidence 时不出现“已运行”、“通过”或“已验证”。
- 至少 24 个 Golden fixtures 按四个 lane 单独报告：P1.0–P1.2 的 12 个 current-lane durable 结果与 P1.3 的 12 个 expected-not-enabled 结果不得混为一个成功率；随后形成明确 P1.4 决策记录。

### Phase 1 明确非目标

- 正式 Test Management、Test IR/BDD/Test Case 系统记录、Release Management 或 Project 强绑定。
- Browser/Device Grid、BrowserStack Adapter、API Runner 或任何真实被测系统执行。
- 远程 Git/PR、缺陷、外部测试管理或生产环境写入。
- 多租户共享服务、通用 RPA 平台、多 Agent 拓扑或供应商模式选择器。

## Phase 2：Test IR 与 Agentic Test Lab

### 交付

- 在单用户/单 Project Lab 中交付最小 Test Authoring、Execution Orchestrator、Result/Evidence Collector 和 RCA 模块；使用本地 Git/worktree、Docker Selenium Grid 和本地/受控测试远端，不把团队 GitHub 副作用当成本阶段前置。
- 定义 Test IR v1、stable Test ID、Git layout、schema migration 和语义 diff。
- 固化 Run/Task/Attempt、Evidence Manifest、Finding、Approval 与幂等契约。
- LangGraph + FastAPI 可作为主 Orchestrator 实验基线；Codex SDK 作为可替换 Code/Workflow Specialist，检索/执行/审查子 Agent 支持固定 DAG 与受控 Agentic Loop。
- 在 Test IR Schema、validator/compiler 就绪后增加 `code-edit` Profile：固定 source revision 与独立 worktree，生成 Draft Test IR、最小语义 patch、local validation commit 和候选代码；本阶段只在本地 Git 或受控测试远端验证发布链，正式 Commit Service/GitHub App 在 Phase 3 产品化。
- 通过统一 Knowledge/Retrieval API 检索、复用和更新已有测试资产，不在 Agent 内复制私有检索链路。
- Ollama 起步并通过 LiteLLM 保持模型契约；高并发时再评估 vLLM。
- Selenium Grid 4 + Docker、Allure + OpenTelemetry + Jaeger；Web 闭环稳定后再接 Appium Device Farm。
- Healenium/自研算法只生成自愈候选，所有修改经过隔离验证和人工审批。

### 出口标准

- 自然语言/BDD → 检索已有资产 → Draft Test IR → local validation commit/Git diff → Browser 执行 → 统一证据 → 单次 RCA/自愈建议 → 人工确认，在 Lab 环境完整跑通。
- 新建与更新已有资产是两条明确路径；更新只生成最小语义 patch。
- 断开外部 SaaS 后仍可运行内网核心闭环。
- Agent 关闭后，确定性执行、断言和证据采集仍能独立工作。

## Phase 3：团队执行 MVP

### 交付

- GitHub App/Webhook、PR/Check 回写、分支与审批流程。
- 将 Phase 2 Lab 的 Platform API/BFF、Session/Intent、Test Authoring、Execution Orchestrator、Result/Evidence Collector 和 RCA 基础模块产品化为多用户、可恢复服务。
- 交付 Commit Service 作为唯一远端 Git 写者；执行 `local validation commit → 确定性验证 → Publish Approval → remote branch/PR`，Agent/Orchestrator 不持有生产 Git 凭据。
- 将 Athena Ingestion 与 Phase 1 Intelligence 已使用的 MySQL operational SoR、transactional Outbox、Outbox Relay、Redis 分发/租约/Reconciler 扩展到 Run/Execution，并完成多用户生产硬化。
- Blob 证据及生命周期策略、Key Vault SecretRef、自建 Browser Grid 和 API/Contract ephemeral worker。
- 新建、复用、更新、执行、诊断五类 Intent Router。
- 在统一 App Shell 和 Intelligence Lab 交互基础上扩展测试工作台：结构化低代码/Test IR editor、IR/代码 diff、Run 时间线、证据、审批和重跑；后置 Knowledge Chat 可作为独立知识入口接入。

### 出口标准

- 重复 GitHub Webhook、Queue 消息和 Worker 重启不会产生重复外部副作用。
- 已有资产可被检索并生成最小语义 patch，再经过隔离验证与 Git review。
- Run 固定 Git commit；Test asset projection 可由 Git 重建，MySQL run/evidence metadata 与 Blob 按 hash 对账。
- 所有 Agent Finding 带模型/提示/工具版本、置信度和 evidence refs。

## Phase 4：企业平台扩展

### 交付

- AKS namespace/node pool、workload identity、private endpoint、NetworkPolicy 与 KEDA。
- 企业 PaaS MySQL、PaaS Redis、Azure AI Search、Blob Storage 和 Key Vault 的生产化治理。
- LiteLLM 无状态多模型路由与 fallback；TAP MySQL 持有策略、用量、预算和审计事实。
- Appium Device Farm gateway、设备占用与健康检查。
- 允许时接入 BrowserStack Adapter，用于外部矩阵或弹性补充。

### 出口标准

- 多租户权限测试证明 MySQL、Search、Redis、Blob 与 Agent context 无跨租户数据泄漏。
- Provider、模型、Worker 和队列故障均有降级、对账、告警和 Runbook。
- 容量、成本、数据保留和灾难恢复达到批准的生产 SLO。

## Phase 5：智能增强与规模化

- 失败指纹、聚类、历史 RCA 与修复效果反馈。
- 代码—测试资产轻量依赖图和可解释风险选测。
- Locator/Step 自愈候选、Vision 辅助和稳定性重复验证。
- Agentic Loop 离线评测：任务完成率、误操作率、安全违规率、成本和人工采纳率。
- 由候选 patch 自动创建 PR；仍不自动合并或制造“假绿”。
- 按真实瓶颈拆分 Ingress、Indexer、Result Pipeline 或 Scheduler，不预先微服务化。
